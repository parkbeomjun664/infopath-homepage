주요 기능

회사 소개부터 도입 문의 접수까지

    번역을 상태가 아니라 경로로 다뤄 /ko, /en이 각각 실제 주소를 가집니다. 링크를 공유해도 언어가 유지됩니다.

  • 검색 노출 스위치

  • SEO · OG 이미지

핵심 구현 & 기술 판단

왜 이렇게 만들었는가

① 정보가 없는 상태를 설계 대상으로

문제 — 오픈 일정은 정해졌는데 사업자 정보 · 대표자 소개 · 실적이 회사에서 오지 않았다.

빠진 값을 빈칸으로 남기면 「대표자 —」가 됩니다. 그건 정보가 아니라 미완성 신호입니다. 값마다 pending 플래그를, 섹션마다 스위치를 두고 확인되지 않은 항목은 렌더링 자체를 건너뛰게 했습니다.

개발 모드에서만 점선 상자로 "여기에 무엇이 들어가야 하는지"를 띄워, 자료가 오면 값만 채우고 플래그를 바꿉니다. 실제로 사업자등록증을 받은 날 코드 수정 없이 푸터 · 회사소개 · 방침 다섯 곳이 한꺼번에 켜졌습니다.

② 문의 폼을 백엔드 없이

문제 — 폼 하나 때문에 상시 서버를 띄우면 비용과 관리 지점이 생긴다.

API Route 하나에서 zod로 서버 사이드 재검증 후 메일을 보냅니다. 클라이언트 검증은 사용성을 위한 것일 뿐 신뢰하지 않습니다.

레이트 리밋과 허니팟 필드를 붙이되, 봇이 걸리면 오류 대신 정상 응답을 돌려줘 탐지를 피하게 했습니다. 메일 발송 모듈에는 server-only를 걸어, 클라이언트로 새면 런타임이 아니라 빌드에서 실패합니다.

③ 다국어를 번역이 아니라 라우팅으로

문제 — 언어를 상태로 두면 공유한 링크가 상대에게 다른 언어로 열린다.

미들웨어로 /ko · /en을 실제 경로로 만들었습니다. 언어별로 메타와 사이트맵이 따로 생성됩니다.

두 메시지 파일은 Record<Locale, typeof ko>로 묶어, 한쪽에만 키를 추가하면 타입 검사에서 걸리게 했습니다. 문구가 400줄을 넘어가면 사람 눈으로는 누락을 못 찾습니다.

④ 전 페이지 정적 생성

문제 — 회사 홈페이지에 상시 서버를 두면 비용과 장애 지점이 함께 는다.

25면을 빌드 시점에 미리 만들고, 런타임 서버 함수는 문의 처리용 하나만 남겼습니다. 공유 카드(OG) 이미지도 디자인 파일로 만들지 않고 코드로 생성해, 문구가 바뀌면 이미지가 따라옵니다.

⑤ 공개하면 안 되는 것을 코드로 막기

문제 — 사내 인프라 도면은 화면에서 빼도 public/에 있으면 URL로 직접 열린다.

목록에서 제외하는 것만으로는 부족해 파일 자체를 public/에서 지우고 저장소 밖에 뒀습니다.

개인정보처리방침이 법무 검토 전이라 robots.txt도 환경변수 하나로 전체 차단해 두고, 확정된 뒤에만 열리도록 했습니다. 초안 상태의 방침이 검색에 잡히면 되돌릴 수 없습니다.

빌드 시점과 런타임의 분리

화면에 나가는 값은 content/ 두 곳에 모여 있고, 나머지는 전부 빌드 시점에 결정됩니다. 런타임에 살아 있는 것은 문의 처리 하나뿐이라 장애 지점과 비용이 그만큼만 존재합니다.

이 프로젝트에서 배운 것

  • 정보가 없는 상태도 설계 대상이라는 것 — 기능보다 "아직 모르는 값"을 어떻게 다룰지가 더 오래 걸렸습니다
  • 추측으로 쓴 문장은 회사의 약속이 된다 — 확인 못 한 수치와 절차는 비워 두는 편이 낫습니다
  • 위험은 코드 밖에도 있다 — 같은 DNS에 걸린 회사 메일처럼, 내 화면 밖의 것을 먼저 확인하는 습관
  • 일정을 지배하는 건 코드가 아니었다 — 자료 수급 속도에 맞춰 켜고 끌 수 있게 만드는 것이 실제 해법이었습니다

핵심 구현 & 기술 판단

왜 이렇게 설계했는가

① 명령형 지도 SDK를 선언형 React에 통합

문제 — 카카오 지도 SDK는 React의 렌더링 방식과 맞지 않는 명령형 라이브러리다.

지도 인스턴스와 마커를 컴포넌트 내부 useRef에 캡슐화하고, forwardRef + useImperativeHandle로 addMarker · drawRoute · clearAll 같은 메서드만 부모에 노출했습니다.

부모는 SDK API를 몰라도 되고, 인터페이스만 지키면 지도 구현체를 교체해도 부모 코드는 그대로입니다. 마커는 SDK가 직접 DOM에 그리므로 useState가 아닌 useRef에 담아 불필요한 리렌더를 없앴습니다.

② 단위가 다른 지표를 함께 비교

문제 — 좌표 평균은 아무것도 없는 곳이 나올 수 있고, 거리 평균이 이동시간 평균과 다르다.

중심점은 검색 시작점으로만 쓰고, 주변 교통 허브(역 · 터미널)를 후보로 여러 개 찾아 평가합니다.

후보마다 공평성(이동시간 편차) · 평균 소요시간 · 교통비를 계산하는데, 단위가 분과 원이라 그냥 더하면 숫자가 큰 비용이 결과를 지배합니다. min-max 정규화(0~1) 후 가중치(공평성 0.5 · 시간 0.3 · 비용 0.2)로 합산했습니다. 가중치는 상수로 분리해 튜닝이 쉽습니다.

③ 병렬 / 순차 절충으로 요청 제한 회피

문제 — 후보 × 멤버를 모두 병렬 처리하면 동시 요청이 폭증한다.

멤버별 경로는 서로 독립적이라 Promise.all로 병렬 처리해, 후보당 소요 시간을 "가장 느린 멤버 한 명" 수준으로 줄였습니다.

다만 후보까지 병렬로 돌리면 동시 요청이 후보수 × 멤버수로 늘어 외부 API의 429에 걸립니다. 멤버는 병렬 · 후보는 순차로 속도와 안정성을 절충했습니다.

④ 상태 영속화 + 버전 마이그레이션

문제 — 저장 형식이 바뀌자 기존 사용자의 화면이 빈 페이지로 죽었다.

상태를 localStorage에 저장하되 일시적 상태(계산 중 여부)는 제외했습니다. 필드가 추가되며 옛 데이터가 undefined.toLocaleString()으로 크래시하자, version과 migrate로 크래시를 유발하는 결과만 비우고 사용자가 입력한 참여자 정보는 보존했습니다. 렌더링 단계에도 방어 코드를 한 겹 더 뒀습니다.

⑤ 비동기 검색의 경쟁 상태 방어

문제 — 반경 필터를 빠르게 바꾸면 늦게 출발한 이전 요청이 최신 결과를 덮어쓴다.

주변 인프라 검색에서 useEffect cleanup의 cancelled 플래그로 낡은 요청의 응답을 상태에 반영하지 않도록 무효화했습니다. 개선 방향으로 AbortController를 통한 요청 자체 취소를 계획하고 있습니다.
