# 참고 사이트 분석 — 여백 · 타이포 · 전개 순서 · 모션

분석 대상: [LS THiRA-UTECH](https://ls-thirautech.com/), [MICube](https://www.micube.co.kr/)
요청하신 4개 항목만 다룹니다. 섹션 구성·그리드·색상·문구·GNB는 분석 대상에서 제외했습니다.

**측정 방법** — 두 사이트의 HTML과 CSS를 직접 내려받아 값을 추출했습니다.
`[측정]`은 CSS에서 실제로 읽은 값, `[추정]`은 측정하지 못해 근거를 들어 추론한 값입니다.

> ⚠️ LS는 WordPress + Salient 테마 + WPBakery 조합이라 섹션 여백이 인라인·동적 클래스·테마 기본값에
> 흩어져 있어 **신뢰할 만한 단일 수치를 뽑지 못했습니다.** 여백 항목은 값이 깨끗하게 나온 MICube를
> 기준으로 삼고, LS는 타이포와 전개 순서에서 주로 인용합니다.

## 1. 여백 비율

### MICube [측정]

CSS가 `vw` 단위로 유동 여백을 쓰고 있어 설계 기준폭을 역산할 수 있었습니다.

| 항목 | 값 | 비고 |
|---|---|---|
| 설계 기준폭 | **1600px** | `font-size: 2.50156vw` = `40px` → 40 ÷ 0.0250156 ≈ 1599 |
| 콘텐츠 컨테이너 | **1200px** | CSS 내 36회 등장 |
| 전체폭 섹션 | 1600px | 42회 등장 |
| 섹션 상하 패딩 | **150px** (최빈) | `9.38086vw`, 4회 — 가장 많이 쓰인 값 |
| 〃 (범위) | 100 / 105 / 150 / 200px | `6.25vw` `6.57vw` `9.38vw` `12.51vw` |

**도출되는 비율**

```
섹션 상하 패딩 ÷ 컨테이너 폭  =  150 ÷ 1200  =  12.5%
컨테이너 폭     ÷ 설계 기준폭  = 1200 ÷ 1600  =  75%
```

여백을 px로 고정하지 않고 `vw`로 묶은 점이 핵심입니다. 화면이 넓어지면 여백도 같이 커져
**여백과 콘텐츠의 비율이 어떤 해상도에서도 유지**됩니다.

### LS THiRA [측정 일부]

| 항목 | 값 |
|---|---|
| 콘텐츠 max-width | **1300px** (CSS 내 12회로 최빈) |
| 광폭 변형 | 1425px, 1500px |
| 섹션 상하 패딩 | 측정 실패 — 위 경고 참조 |

### 우리 현재 값

| 항목 | 현재 | MICube 기준 |
|---|---|---|
| 컨테이너 | 1200px | 동일 ✓ |
| 섹션 상하 패딩 (아키텍처) | 96px / 128px(lg) | 150px보다 **좁음** |
| 좌우 여백 | 24px / 64px(lg) | — |
| 히어로 상하 패딩 | 144px / 176px(lg) | 150px 대비 적정 |

## 2. 타이포 위계

### MICube [측정]

`vw`와 `px`를 함께 선언해 유동 크기를 씁니다.

| 역할 | 크기 | weight | line-height |
|---|---|---|---|
| 대제목 | 43px (`2.68918vw`) | — | — |
| 제목 | 40px (`2.50156vw`) | — | — |
| 중제목 | 36px (`2.25141vw`) | — | — |
| 소제목 A | 24px | **700** | 1.46 |
| 소제목 B | 23px | **500** | 1.52 |
| 본문 | 16px / 18px | 400 | — |

### LS THiRA [측정]

사용 중인 크기: `44 · 36 · 32 · 30 · 28 · 25 · 24 · 22 · 20 · 18 · 14 · 13px`
서체: Nanum Gothic (400/700/800), Noto Sans KR (300/500/700)

### 도출되는 비율

```
MICube   제목 43px : 본문 16px  =  2.69 : 1
MICube   제목 40px : 본문 18px  =  2.22 : 1
LS       제목 44px : 본문 16px  =  2.75 : 1
                              ─────────────
             두 사이트 공통 대역  ≈  2.2 ~ 2.8 : 1
```

**weight 대비** — 두 사이트 모두 제목 **700** vs 본문 **400**. 300단계 차이로 위계를 만들고,
중간 단계(500)는 소제목에만 씁니다. 크기보다 굵기 대비를 먼저 씁니다.

**line-height** — 제목에도 **1.46~1.52**를 줍니다. 한글은 영문보다 글자 높이가 커서
1.2 이하로 조이면 줄이 붙어 보인다는 판단으로 읽힙니다.

### 우리 현재 값

| 항목 | 현재 | 참고 사이트 대역 |
|---|---|---|
| 히어로 제목 : 본문 | 64px : 18px = **3.56 : 1** | 2.2~2.8 : 1 → **과함** |
| 아키텍처 제목 : 본문 | 40px : 18px = 2.22 : 1 | 적정 ✓ |
| 제목 weight | 500 | 700 → 대비 약함 |
| 본문 weight | 400 | 400 ✓ |
| 제목 line-height | 1.35 | 1.46~1.52 → 다소 좁음 |

## 4. 스크롤 애니메이션 — 이동 거리와 지속 시간

### MICube [측정]

CSS 내 `transition`/`animation` 지속시간 분포:

| 값 | 횟수 | 용도 추정 |
|---|---|---|
| 0.3s | 14 | hover·UI 전환 (최빈) |
| 0.2s | 12 | 미세 전환 |
| 0.5s | 7 | 중간 전환 |
| **1.2s** | 2 | 슬라이더·스크롤 등장 [추정] |

> 0.3s가 최빈이지만 대부분 hover 전환입니다. **스크롤 등장에 해당하는 값은 1.2s 쪽**으로 보입니다.

### LS THiRA [측정]

- 등장 방식: `fade-in-from-bottom`
- 속도 설정: `medium`
- delay: `0` (요소별 stagger 없음)

Salient 테마의 `medium`은 통상 **0.7s**입니다 [추정 — 테마 문서 미확인].

### 이동 거리

두 사이트 모두 **CSS가 아닌 JS에서 처리**해 정적 분석으로 값을 얻지 못했습니다.
LS의 `fade-in-from-bottom`은 아래에서 위로 올라오는 형태이며, 통상 20~40px 범위입니다 [추정].

### 우리 현재 값

| 항목 | 현재 | 참고 대역 |
|---|---|---|
| 등장 지속시간 | 700ms | LS 700ms [추정] ✓ · MICube 1200ms |
| 이동 거리 | 32px | 20~40px [추정] ✓ |
| easing | cubic-bezier(.16,1,.3,1) | — |
| stagger | 100ms | LS는 0 (stagger 없음) |

# 우리 사이트 적용 제안

인포패스는 **"부담 없이 시작하는 MES"**로 설득합니다. 규모가 아니라 진입 장벽 낮추기입니다.
따라서 같은 여백·타이포 원칙을 쓰되 **섹션은 더 적게, 여백은 더 크게** 가져갑니다.
섹션이 적을수록 각 섹션에 숨 쉴 공간을 줘야 빈약해 보이지 않습니다.

## 제안 A — 섹션 여백 확대 `권장`

| 대상 | 현재 | 제안 | 근거 |
|---|---|---|---|
| 섹션 상하 패딩 (기본) | 96px | **120px** | MICube 150px의 80%. 모바일 기준 |
| 섹션 상하 패딩 (lg) | 128px | **176px** | 150px보다 **넓게** — 섹션 수가 1/3이므로 |
| 컨테이너 | 1200px | 유지 | MICube와 동일 |
| 좌우 여백 | 24 / 64px | 유지 | |

**비율 확인** — 176 ÷ 1200 = **14.7%** (MICube 12.5%보다 여유)

## 제안 B — 히어로 제목 비율 조정 `권장`

현재 3.56:1은 참고 대역(2.2~2.8:1)을 크게 벗어납니다. 두 가지 방향이 있습니다.

| 안 | 제목 | 본문 | 비율 | 효과 |
|---|---|---|---|---|
| B-1 | 40~**56px** | 18px | 3.11:1 | 제목만 줄임 |
| B-2 `권장` | 40~**56px** | **20px** | **2.80:1** | 본문도 키워 대역 안으로 |

B-2를 권합니다. 본문 18→20px는 "부담 없이"라는 메시지에 맞게 **읽기 편한 인상**을 만듭니다.

## 제안 C — weight 대비 강화 `검토 필요`

참고 사이트는 제목 700 / 본문 400으로 300단계 차이를 씁니다.
우리는 500 / 400으로 100단계뿐이라 위계가 약합니다.

다만 **직전에 "700 → 500으로 낮춰달라"고 지시하신 항목**입니다.
부드러운 인상을 유지하면서 위계를 만드는 절충안:

| 안 | 제목 weight | 비고 |
|---|---|---|
| C-1 | 500 유지 | 지시 유지. 대신 크기·여백으로만 위계 |
| C-2 `권장` | **600** | 700의 무거움 없이 대비 확보 |

## 제안 D — 제목 줄간격 `권장`

제목 line-height **1.35 → 1.45**. 참고 사이트 대역(1.46~1.52) 진입.
한글 제목이 2줄이므로 체감 차이가 큽니다.

## 제안 E — 정보 전개 순서 `구조 확정`

두 참고 사이트에서 도출한 원칙을 우리 포지셔닝에 맞게 변형합니다.

```
Hero          이슈 제기      ← LS 방식 채택
Challenge     문제 정의      ← 우리 강점. LS보다 비중 확대
Solution      해법           ← 벽 3개에 1:1 대응
Architecture  근거 (기술)    ← 근거는 해법 뒤 (양쪽 공통 원칙)
Industry      근거 (적용)
CTA           행동           ← 마지막 단독 (양쪽 공통 원칙)
```

비중: 문제 제기 **33%** · 해법 17% · 근거 33% · 행동 17%
→ MICube(문제 제기 0%)와 정반대. 진입 장벽을 낮추려면 **장벽을 먼저 말해야** 합니다.

## 제안 F — stagger 축소 `선택`

LS는 stagger가 아예 없습니다(delay 0). 우리 100ms는 항목이 6개일 때 마지막이 500ms 늦어져
스크롤 속도가 빠르면 덜 나타난 채로 지나갑니다. **100ms → 60ms** 또는 상한 3개까지만 적용을 권합니다.
