색을 감으로 고르지 않고 제공받은 로고·배경 이미지의 픽셀을 직접 분석해 팔레트를 뽑았습니다. 네이비 #003060, 그린 #48A830, 애저 #1878C0가 실제 브랜드 색이었고, 이를 Tailwind 토큰과 CSS 변수 두 겹으로 정의해 컴포넌트는 시맨틱 토큰만 참조하도록 했습니다.

번역 누락을 컴파일 단계에서 차단

영문 메시지 파일이 국문 파일의 구조를 타입으로 강제하도록 설계했습니다. 키가 하나라도 빠지면 런타임이 아니라 빌드가 실패합니다. 

const en: Messages = { ... }   // Messages = typeof ko
// 키 누락 시 tsc 에러 → 배포 자체가 막힘

모션은 리스너 하나로 공유

패럴랙스 요소마다 스크롤 리스너를 붙이면 스크롤이 무거워집니다. 단일 requestAnimationFrame 루프를 모듈 싱글턴으로 두고 요소가 등록하는 구조로 만들었으며, 동시 대상 3개로 상한을 두었습니다. will-change는 실제로 움직이는 동안에만 켜고 180ms 유휴 후 해제합니다.

근거 없는 수치는 쓰지 않음

"도입 기간 60% 단축" 같은 문구를 쓰지 않았고, 실적 수치·고객사 로고 섹션은 컴포넌트만 만들고 플래그로 꺼두었습니다. 제조 IT 업계는 문의 단계에서 수치가 바로 검증되고, 로고 무단 게재는 실제 분쟁 사유이기 때문입니다. 자료가 확보되면 플래그만 켜면 됩니다.

환경변수에 섞인 BOM 한 글자

증상
로컬은 통과, Vercel에서만 /ko/about 프리렌더 실패. 오류 메시지는 프로덕션 빌드라 가려짐.
추적

원인
EF BB BF (UTF-8 BOM)가 값 앞에 붙어 new URL()이 예외를 던졌고, 그 호출이 layout의 generateMetadata에 있어 전 페이지가 깨졌습니다. about은 첫 번째로 보고된 것뿐이었습니다.
조치
환경변수 정리 유틸을 만들어 BOM·공백을 걷어내도록. API 키에 BOM이 붙으면 인증이 조용히 실패하므로 특히 중요합니다.

품질 · 공개 전 차단

사이트가 사실이 아닌 것을 말하고 있었다

발단
회사에서 받은 아키텍처 도면을 근거로 기술 사양을 작성했는데, 개발팀 문서에 그 도면이 목표(To-Be) 구조이고 현재 구현(As-Is)은 다르다는 사실이 명시돼 있었습니다.
점검
라이브 페이지의 기술 주장을 전수 추출해 실제 코드·의존성과 대조했습니다. 15건이 사실과 달랐습니다 — 설비 연동(OPC UA·Modbus·MQTT), 데이터 저장(InfluxDB·DuckDB·MinIO), 배포(Docker·Kubernetes), 모니터링(Prometheus·ELK), AI 예측 5종.
판단
MES 도입 검토에서 설비 연동은 1순위 확인 항목입니다. 기술 검증(PoC)에서 한 항목이 걸리면 나머지 설명의 신뢰도까지 함께 떨어집니다. 「확장 로드맵」으로 옮기는 안도 검토했으나, "예정"이라 써도 "언제요?"를 부르고 답할 수 없으면 그 자리에서 신뢰가 깎이므로 제외했습니다.
조치
거짓 주장은 삭제. 도면은 「목표 구조 기준」으로 명시해 현재 구현과 분리. FAQ의 설비 연동 답변을 "대부분 가능합니다"에서 실제 제공 범위(REST API)와 개별 협의 사항으로 다시 작성.
결과
렌더링 본문 기준 금지 표현 0건. 남은 언급 2곳은 To-Be 표시 구역과 FAQ의 정직한 답변뿐

리뷰 반영 · 원인 규명

"로고가 튄다"를 파일 문제로 좁히다

피드백
현업 실무자가 배포본을 보고 네 가지를 지적했습니다. 그중 하나 — "처음에 PC에서 열었을 때 로고 배경이 흰색인데 주변이 회색계열이라 튄다. 살짝 휠 돌리면 괜찮아진다."
관찰의 값어치
「휠 돌리면 괜찮다」가 결정적인 단서였습니다. 스크롤하면 헤더가 흰 배경으로 바뀝니다. 즉 최상단에서 헤더가 투명할 때만 문제가 드러난다는 뜻이었습니다. 코드만 보고 있으면 못 잡는 조건입니다.
규명
로고 PNG를 픽셀 단위로 열어봤습니다. 알파 채널은 있는데 투명 픽셀이 0%, 76%가 불투명 흰색이었습니다. 투명을 담을 그릇은 있는데 내용물이 흰색이었던 것입니다.
조치
전역으로 「흰색 → 투명」을 걸면 로고 안쪽 흰 부분(공장 아이콘 내부)까지 뚫립니다. 가장자리에서 시작하는 채우기(flood fill)로 바깥과 이어진 흰색만 제거하고, 경계의 안티에일리어싱 픽셀 1,465개는 밝기에 비례해 반투명 처리했습니다.
정정한 것
같은 피드백에 원인 추정이 두 군데 빗나가 있었습니다. ① "avif가 투명을 지원하니 그 포맷을 쓰면" → 포맷 문제가 아니었고 PNG도 이미 투명을 담을 수 있었습니다 ② "흰색에 투명도를 적용하면" → CSS 투명도는 이미지 전체에 걸려 로고 색까지 바랩니다. 세 가지 경우를 렌더링해 비교 이미지로 설명했습니다.
결과
투명 0% → 76.2%. 로고 안쪽 흰색 1%는 의도적으로 보존

Architecture

구조 진단

회사 홈페이지가 제품 카탈로그로 읽힌다

증상
메인 9개 블록 중 5개가 자체 플랫폼 설명이었습니다. 처음 본 사람은 "이 회사 = MES를 파는 회사"로 이해합니다.
실제 관계
회사는 스마트팩토리를 구축해 주는 곳이고, 자체 플랫폼은 그 구축을 빠르게 만드는 자산입니다. 파는 것이 제품이 아니라 구축입니다.
왜 중요한가
제품을 팔면 대기업 패키지와 기능 비교 싸움이 됩니다. 구축을 팔면 "백지에서 시작하지 않아 빠르고 저렴하다"는, 패키지가 할 수 없는 이야기가 됩니다. 같은 기능을 다른 위치에 놓는 문제였습니다.
조치
제품 상세를 전용 페이지로 분리(/solution → /infolink, 308 영구 리다이렉트로 기존 링크 보존)하고 메인에는 진입 블록 하나만 남김. 문제 3개와 해법 4개로 짝이 맞지 않던 두 섹션을 카드 3장으로 통합. 아키텍처·기술 사양은 요약만 남기고 상세는 제품 페이지가 흡수.
결과
메인 블록 9 → 6개, 렌더 텍스트 190줄 → 94줄

부수적으로, 사진이 없어 글만 이어지던 구간에 이미지 밴드를 넣고 본문에 묻혀 있던 결론 문장을 사진 위로 올렸습니다. 카드마다 3줄씩 붙어 있던 근거 문단은 접어 두어(<details>) 훑을 수 있게 하되 검색엔진·스크린리더에는 그대로 노출되도록 했습니다.

  • prefers-reduced-motion을 전 구간에 대응. 움직임을 꺼도 콘텐츠는 반드시 보이도록 별도 규칙을 두었습니다 — 애니메이션만 끄면 등장 전 상태(투명)에 갇힙니다.
  • JS가 꺼진 환경을 위한 <noscript> 폴백. 같은 이유입니다.
  • 라이트박스에 ESC 닫기 · 포커스 이동과 복귀 · 배경 스크롤 잠금.
  • 도면을 이미지로만 두지 않고 계층 구조를 텍스트로도 실었습니다. 스크린리더와 검색엔진이 읽을 수 있어야 하기 때문입니다.
  • SVG 라벨 크기를 뷰박스 배율로 역산해 어느 폭에서도 14px 이상이 되도록 설계.

스팸·법적 요건

  • 허니팟 필드 — 봇에게는 성공으로 응답하고 발송하지 않습니다. 실패를 알려주면 우회를 학습하기 때문입니다.
  • IP 기준 rate limit. 서버리스에서 인스턴스별로 센다는 한계를 코드에 명시하고 대안(외부 저장소)을 함께 적어두었습니다.
