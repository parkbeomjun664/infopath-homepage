### 6. 검색에서 내리기 — 플래그를 끄는 것이 답이 아니었음

**처음 생각** — 세션 1에서 만든 `NEXT_PUBLIC_ALLOW_INDEXING`을 끄면 된다.

**확인해 보니 틀렸습니다.** 그 플래그의 차단 모드는 두 가지를 동시에 했습니다.

| | 끄면 생기는 일 |
|---|---|
| `robots.txt` | `Disallow: /` — 크롤러 접근 자체를 금지 |
| 메타 태그 | `noindex, nofollow, nocache` |

**이 둘은 반대 방향으로 움직입니다.** 크롤링을 막으면 크롤러가 페이지를 가져갈 수 없어
`noindex`를 **읽지 못합니다.** 그러면 이미 등록된 주소는 색인에 그대로 남고,
제목·설명만 사라진 「이 페이지에 관한 정보가 없습니다」 상태로 굳습니다.

세션 1에서 공개 직후 관찰했던 그 상태([검색 노출 경과 관찰](#검색-노출-경과-관찰) 항목)가
정확히 이것이었습니다. 차단 기간의 흔적이라고 적었는데, 원인은 **차단 방식 자체**였습니다.
구글 문서도 robots.txt 차단은 색인 삭제 수단이 아니고 영구 제거는 `noindex`라고 명시합니다.

> **빼려면 먼저 읽히게 해야 합니다.** 크롤링을 열어두고 `noindex`로 빼라고 지시해야
> 색인에서 실제로 사라집니다.

**결정 · 판단**

| 사안 | 결정 | 이유 |
|---|---|---|
| 차단 방식 | `hidden`에서 **크롤링 허용 + noindex** | 위 그대로. 막으면 빠지지 않음 |
| 모드 개수 | 2단계(허용/차단) → **3단계** | 「공개」와「완전 차단」 사이에 「빼는 중」이 빠져 있었음. 이 상태를 표현할 수 없어서 잘못된 조합이 나왔음 |
| `blocked` 유지 여부 | **남겨둠. 단, 소멸 확인 후에만 사용** | 전체 차단 자체가 틀린 게 아니라 **순서**가 틀렸던 것. 다 빠진 뒤에는 유효한 상태 |
| `sitemap.xml` | **`hidden`에서 유지** | 크롤러가 빨리 다시 와서 `noindex`를 읽고 가야 색인이 빨리 빠짐. 치우는 것은 `blocked`로 넘어갈 때 |
| 응답 헤더 | `X-Robots-Tag: noindex` **추가** | `public/`에 고객사 로고 4개와 **아키텍처 도면**(`architecture-solution.png`)이 있음. 이미지에는 메타 태그를 달 수 없어 본문만 빠지고 이미지 검색에는 남음 |
| 헤더 예외 | `sitemap.xml` · `robots.txt` **제외** | 크롤러를 불러들여야 하는 경로에 `noindex`를 붙이는 건 목적과 어긋남. 둘 다 검색 결과에 뜨는 문서도 아님 |
| 레거시 변수 | `ALLOW_INDEXING=true` → `public` **호환 유지** | Vercel에 이미 등록돼 있음. 호환이 없으면 환경변수를 바꾸기 전에 배포된 빌드가 `blocked`로 떨어져 **의도치 않은 전체 차단**이 됨 |
| 모드 판단 위치 | `lib/indexing.ts` **한 파일** | 세션 1의 사고가 플래그 하나를 두 곳(robots.txt·메타)에서 각자 해석해 생긴 것. 기준이 갈라지면 또 어긋남 |

**세 모드 전부 빌드해서 응답을 확인했습니다.** 추측으로 둔 동작은 없습니다.

| 모드 | robots.txt | 메타 | X-Robots-Tag | sitemap |
|---|---|---|---|---|
| `public` | `Allow: /` | `index, follow` | 없음 ✅ | 8 URL |
| `hidden` | `Allow: /` | `noindex, nofollow` | 페이지·이미지 모두 ✅ | 8 URL |
| `blocked` | `Disallow: /` | `noindex, nofollow` | 있음 | 없음 |

레거시 변수만 있는 경우(`mode` 미설정 + `ALLOW_INDEXING=true`)도 `public`으로 떨어지는 것을
확인했습니다 — 현재 운영 상태가 그대로 재현됩니다.

`next.config.ts`에서 `./lib/indexing`을 **상대 경로로** 가져옵니다. 이 파일은 Next가 앱 번들과
별도로 읽어서 `@/` 별칭이 해석되지 않습니다. `lib/indexing.ts`가 `lib/env.ts` 하나만
(역시 상대 경로로) 쓰는 이유도 이것입니다. 빌드로 확인했습니다.

**⚠ 기억해야 할 함정**

Search Console의 **임시 삭제는 약 6개월 뒤 자동으로 풀립니다.** 가리는 것일 뿐 빼는 것이
아닙니다. 실제로 빼는 일은 `noindex`가 합니다.
→ 그 안에 `public` 복귀든 `blocked` 전환이든 **결론을 내야 합니다.** 방치하면 조용히 다시 뜹니다.
→ 다시 공개할 때는 **임시 삭제 요청을 취소**해야 합니다. 안 하면 코드가 공개로 돌아와도 계속 가려집니다.

실행 순서는 [deploy.md](deploy.md) 9장에 절차로 정리했습니다.

### 검색 노출 — 현재 `hidden` 전환 대기

세션 1에 적어둔 「재수집되면 해소됨」은 **원인 진단이 틀렸습니다.**
차단 기간의 흔적이 아니라, 차단 방식(robots.txt 차단 + noindex 동시)이 만든 상태였습니다.
경위는 세션 2 참고.

절차는 [deploy.md](deploy.md) 9-2.

**2026-10-05 완료**

1. ✅ Vercel Production에 `NEXT_PUBLIC_INDEXING_MODE=hidden` 등록 → Redeploy
   (Type은 `Config`. `NEXT_PUBLIC_` 값은 브라우저 번들에 박히므로 Secret이 될 수 없고,
   앞으로 계속 바꿀 설정이라 값을 다시 읽을 수 있어야 함)
2. ✅ 배포본 검증 — 전부 통과

   | 항목 | 결과 |
   |---|---|
   | robots.txt | `Allow: /` (크롤러 들여보냄) |
   | 메타 | `noindex, nofollow, nocache` |
   | X-Robots-Tag | 전 페이지 + 이미지(도면·고객사 로고) |
   | sitemap.xml · robots.txt | 헤더 없음 · 8 URL 유지 |
   | 방문자 | 전 페이지 200 |
   | 소유권 확인 파일 | 구글·네이버 200 — **안 깨짐** |

**남은 일**

3. Search Console — URL 검사로 `noindex` 인식 확인 → 임시 삭제 요청
4. 네이버 — 요청 → 웹페이지 수집으로 재수집 유도
5. 주 1회 `site:` 검색으로 색인 소멸 관찰

⚠ 임시 삭제는 **6개월 뒤 자동 해제**됩니다. 그 전에 복귀냐 `blocked`냐를 정해야 합니다.

## 이 프로젝트의 원칙

작업하면서 반복해서 적용한 기준입니다.

1. **확인되지 않은 값은 쓰지 않는다.** 추측으로 쓴 문장은 곧 회사의 약속이 됨
2. **비어 있으면 자리를 비우지 말고 섹션을 숨긴다.** 빈 값은 정보가 아니라 미완성 신호
3. **적어둔 것과 실제가 다르면 그게 위반이다.** 회신 기간, 보관 기간, 방침 모두 해당
4. **코드 밖의 위험을 먼저 본다.** 같은 DNS의 회사 메일, 고객사 로고의 상표권, 공개된 사내 도면
5. **막는 것과 빼는 것은 다르다.** 접근을 차단하면 「빼라」는 지시도 전달되지 않음.
   설정을 바꿨다고 효과가 난 것이 아니라 **응답을 확인해야** 난 것
